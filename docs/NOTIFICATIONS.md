# Notifications

## Confirmed gap, fixed: notification taps went nowhere

The backend was already doing its job correctly — `sendPushToUser` (`src/services/push.js`) is a real, generic helper, and every call site checked (`routes/room.js`'s party invite, `lib/eventReminders.js`, `sockets/syncHandler.js`'s friend-online ping) already sends a structured `data: {type, roomId}` payload alongside the notification. The gap was entirely client-side: `push_notifications.dart` only ever requested permission and registered the FCM token — nothing in the app listened for `FirebaseMessaging.onMessageOpenedApp` or checked `getInitialMessage()`, the two APIs that tell a Flutter app a notification was actually tapped. A `roomId` was being sent with every relevant push and never once read. Tapping "John invited you to a watch party" almost certainly just opened the app to its default screen.

**Fixed**: `lib/core/app_navigator.dart` adds a `navigatorKey` (mirrors the existing `scaffoldMessengerKey` pattern in `app_messenger.dart` exactly — same reasoning: code with no `BuildContext` of its own needs a way to navigate) and `handleNotificationTap(data)`, which reads `data['roomId']` and pushes `PartyScreen`. `push_notifications.dart` now wires both real tap scenarios: `onMessageOpenedApp` (app was backgrounded, user tapped) and `getInitialMessage()` (app was fully killed, the tap is what cold-started it) — the latter deferred to a post-frame callback since the Navigator doesn't exist yet that early in a cold start.

## What's still not covered

- Only room-related notification types (`room_invite`, `event_reminder`, `friend_online`) carry a `roomId` today, confirmed by checking every backend call site. Other notification types (gift received, follow, match) weren't confirmed to carry deep-link-able data — `handleNotificationTap`'s current design (look for `roomId`, no-op otherwise) is a safe default for those: it does nothing rather than navigating somewhere wrong, but doesn't yet route a gift/match notification to its own relevant screen (Wallet, Match chat). A reasonable next step, not attempted this phase since it wasn't confirmed which of those notification types would benefit from a distinct destination versus just opening the app normally.
- Not verified against a real device or an actual FCM push — this is Dart-only code reasoned about and compile-verified (`flutter analyze`, `flutter test`), not confirmed against a real notification tap on a phone. The logic (read a field, push a route) is about as low-risk as this kind of gap gets, but "the code should work" and "it was seen working" remain different claims, consistent with every other client-side fix in this project that couldn't be run on a device.
