# Party architecture

## Two layers (same pattern as PLAYBACK.md)

**The real, live system**: `ActiveRoomHolder` (`lib/core/active_room_holder.dart`) + `RoomSocketController` (`lib/screens/party/room_socket_controller.dart`) + `socket_service.dart`. This is what every screen actually uses today, and what this document's realtime-recovery fix was applied to.

**The new interface layer**: `lib/features/party/domain/{party_session,party_engine,queue}.dart` + `lib/features/party/data/{party_engine_impl,party_realtime_adapter,socket_party_realtime_adapter}.dart`. Wraps the real system (see `INSYNC_MIGRATION_MAP.md`); not yet consumed by any screen. `PartyEngine.changeMode()` and `.sendReaction()` intentionally throw `UnimplementedError` rather than fake success — see that file's own comments for exactly what's missing (an explicit mode-transition path, and a `reaction:send` backend event that doesn't exist yet).

## Realtime recovery (this phase)

**The gap, confirmed by direct code inspection before writing any fix:** `socket_io_client` reconnects the underlying transport automatically after a drop — infinite attempts, exponential backoff (1s up to 5s), no configuration needed, it's the package default. But nothing in the app ever noticed that reconnection happen and re-joined the room or refreshed state. A user's socket could drop, silently reconnect seconds later, and the app would just sit on stale roster/queue/playback data indefinitely — no crash, no error, just silently wrong state — until something unrelated (e.g. leaving and re-entering the screen) forced a fresh `RoomSocketController` to be constructed.

**The backend already does its part correctly** — `syncHandler.js`'s `room:join` handler runs the identical full path whether this is someone's first join or a rejoin mid-session (the `alreadyPresent` check only gates the "X joined" chat message, not the state resend), unconditionally sending back a fresh `queue:state`, `poll:state`, `room:hostChanged`, `call:state`, `room:settingsChanged`, corrected `playback:state`, and `queue:skipVoteState`, plus broadcasting a fresh `presence:roster` to the whole room (including the rejoining socket itself, confirmed by checking `socket.join(roomId)` happens before that broadcast). A separate `playback:requestState` → `playback:state` round trip exists too, for refreshing just playback without a full rejoin. None of this needed to change.

**The fix**: `RoomSocketController` now listens for its own socket's `connect` event (fired again by the client library on every successful reconnect, not just the first connection) and re-emits `room:join` + re-syncs the clock offset — skipping only the very first `connect`, which the constructor already handled synchronously. A `reconnecting` bool flips true on `disconnect`, false once a fresh `presence:roster` actually lands (the first reliable signal a rejoin succeeded, not a fixed timer).

**A subtlety that would have caused a real regression if missed**: `SocketService` (`core/socket_service.dart`) already listens to this same *shared, app-wide* socket's `connect`/`disconnect` events for its own `isConnected` tracking. The event emitter package this app uses removes **every** listener for an event name when `.off(eventName)` is called with no handler argument — confirmed by reading `EventEmitter.off()`'s source directly, not assumed. `RoomSocketController.leave()` already calls `.off('presence:roster')`-style cleanup for every event it listens to; naively adding `.off('connect')`/`.off('disconnect')` there would have silently broken `SocketService`'s connection-status tracking for the rest of the app session every time any room was left. Fixed by registering named instance-method tear-offs (`_onSocketConnect`/`_onSocketDisconnect`) instead of inline closures, so `leave()` can remove precisely those two listeners by reference and nothing else's.

## What's deliberately not done yet

- **No UI consumes `reconnecting` yet.** `party_screen.dart` is a large, complex, live file, and a purely visual addition (a "Reconnecting…" banner) carries real layout-regression risk with no device available to check it renders correctly. The field is there, documented, ready for a follow-up pass — see the existing `_justResumed` "catching up" banner pattern already in `sync_video_player.dart` for a precedent to follow.
- **No automated test for the reconnect logic itself.** `RoomSocketController` takes a real `io.Socket?` from the `socket_io_client` package, which isn't trivially fakeable without a mocking library this project doesn't currently depend on (`mockito`/`mocktail`). Adding a low-confidence mock just to claim test coverage would be worse than being explicit about the gap. If real device/integration testing becomes available, this is the first thing to verify: kill the network, confirm the socket reconnects, confirm the room actually re-syncs instead of sitting stale.
- **No backend changes.** `syncHandler.js`'s disconnect handler still removes a user from the roster immediately with no grace period (confirmed in `FLING_AUDIT.md`'s findings) — a host who drops for even a few seconds triggers an immediate host-transfer server-side, before their own client even notices the drop and starts reconnecting. That's a real gap against the request's Step 29 ("party remains alive... host grace period"), but it's backend Node/Express code serving production traffic on Railway — not something to touch in the same pass as a client-side fix, and out of scope for "realtime recovery" on the client specifically. Flagged here as the natural next backend-side follow-up.
