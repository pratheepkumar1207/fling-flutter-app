# Voice

## What's already real (confirmed by direct code review, not assumed)

Spec Step 12 asks for "Party → VoiceSession → WebRTC → SFU" with mute/unmute/raise-hand/approve/deny/remove-speaker/force-mute. Almost all of it already exists and is production-appropriate:

- **Real SFU, real engine**: `VoiceChatController` (`lib/screens/party/voice_chat_controller.dart`) drives an actual `agora_rtc_engine` instance — `createAgoraRtcEngine()`, `engine.initialize(...)`, `engine.joinChannel(...)`, `muteLocalAudioStream(...)`. Not state-only bookkeeping.
- **Real, correctly-scoped channel tokens** — not a hardcoded/null token. `POST /calls/token` (`src/routes/calls.js`) checks `canJoinRoom(room, userId)` before minting anything, uses the *room's own id* as the Agora channel name (not a client-supplied value — the code's own comment documents this as a deliberate fix for a prior vulnerability), and returns a real `RtcTokenBuilder`-minted token with a 1-hour expiry. This is the right shape for production Agora usage.
- **Every privileged voice action is host-gated server-side**: `call:approveMic`, `call:denyMic`, `call:inviteMic`, `call:removeMic`, `call:forceMute`, `call:forceUnmute` (`syncHandler.js` ~1266-1336) all start with `if (!isHostOf(roomId, userId)) return;`. `call:requestMic`/`call:cancelMicRequest` are open to any participant (raise-hand should be), gated only by the room's `micEnabled` setting.
- **Mute/unmute, raise-hand, approve/deny, remove, force-mute** all exist end to end, client method → socket event → host-gated handler → broadcast `call:state`.

## What was fixed this phase

**The bug**: `VoiceChatController._init()`'s entire body was wrapped in a bare `catch (_) {}` with the comment "voice chat just won't work this session — not fatal to the room." That catches *everything*, indiscriminately — a denied microphone permission, a failed `/calls/token` request, a rejected `joinChannel` call, all looked identical from the outside: `_joined` silently stays `false`, nothing tells the caller why, no event handler was registered at all so even a connection that dropped *after* a successful join had no way to signal that. (The sibling `live_broadcast_controller.dart` has the exact same pattern — not touched this phase, since Live is a separate later spec step, but it's the same fix when that phase comes up.)

**Important nuance, found by reading the surrounding comments in full before touching anything**: the lazy `ensureInitialized()` deferral (not calling `_init()` from the constructor) is not incidental — it's a deliberate, documented workaround for a real native crash: this app's pinned Agora version (6.3.2) crashes the whole process at `engine.initialize()` on some devices, a native-side crash a Dart `try/catch` cannot intercept at all. That part of the design is correct and was **not** changed. What *was* silently swallowed alongside that unfixable case were several genuinely catchable Dart-level failures (permission denial, HTTP failures fetching a token, `joinChannel` rejecting) that have nothing to do with the native-crash risk and deserved real handling.

**The fix**: `VoiceChatController` now extends `ChangeNotifier` (previously a plain class — additive change, nothing wraps it in a provider anywhere so this can't break existing usage) and exposes a `VoiceChatStatus status` (`idle/connecting/connected/permissionDenied/failed`). Microphone permission denial is checked and reported *before* attempting to touch the Agora engine at all, rather than letting it surface as a generic downstream failure. A real `RtcEngineEventHandler` with `onError` is now registered — the first place in this codebase `onError` is used at all (the existing `onUserJoined`/`onUserOffline` pattern in `live_broadcast_controller.dart` only tracks the remote video feed, it doesn't handle connection errors either) — so a post-join connection failure now actually flips `status` to `failed` instead of leaving `_joined` permanently (and wrongly) `true`.

**Deliberately not done**: no UI in `party_screen.dart` consumes `status` yet, for the same reason as `RoomSocketController.reconnecting` in the realtime-recovery phase — `party_screen.dart` is large and live, and `VoiceChatController` was never previously a `ChangeNotifier` at all (nothing was reactively listening to it before), so wiring a visible "mic connection failed" indicator is new UI surface, not a fix to something already half-wired. The field is there, real, and ready for that follow-up.

## What's confirmed missing, and why it wasn't built this phase

Spec Step 12 asks for five roles: Host, Co-host, Moderator, Speaker, Listener. **The backend has exactly two:** `isHostOf(roomId, userId)` (`syncHandler.js`) is `roomHosts.get(roomId) === userId` — one host id per room, full stop. There is no co-host, no moderator, anywhere in the backend's voice/call logic — every privileged action is gated on being *the* host, not *a* host-tier role. On the client, `PartyRole` (`lib/features/party/domain/party_session.dart`) declares `host`/`coHost`/`moderator`/`speaker`/`member`, but by that file's own comment, `speaker` is "a placeholder for when that gets unified, not yet wired to anything" — and confirmed by tracing every construction site, `coHost` and `moderator` are never actually assigned anywhere in the app. `experience_hub.dart`'s "Co-hosts" button opens a placeholder snackbar, not a real feature.

This is a real, substantial gap — and it's a redesign, not a patch. Every one of the six host-gated `call:*` handlers, plus whatever `room:*`/`queue:*` handlers should also extend to a co-host or moderator tier, would need `isHostOf`'s binary check replaced with a real per-user role lookup, in a 1360-line production socket file serving live traffic, with no staging environment or device available in this sandbox to verify a permission-model change doesn't lock hosts out of their own rooms or let the wrong people in. That risk profile is categorically different from this phase's other fixes (an error-handling gap with a clear, narrow, additive correction) and from the `PartySession`/`PartyEngine` wrapper work earlier in this project (new, additive interfaces around working code). Attempting it blind here would be exactly the kind of "claim completion because files compile" the request explicitly warns against. Scoped as follow-up work, not attempted this phase.

## One thing only the user can verify

Whether Agora's *primary certificate* enforcement is actually turned on for this App ID in the Agora console. The server-side code is correct (it mints and requires a real token), but Agora's own docs are clear that an App ID without certificate enforcement enabled will still accept `null`/dummy tokens directly from the raw SDK, bypassing this backend's `/calls/token` gate entirely for anyone who extracts the App ID from the compiled app (which is expected to be visible — it's not a secret) and calls the Agora SDK directly. This is an Agora-console configuration setting, not something visible or fixable from this repository's source.
